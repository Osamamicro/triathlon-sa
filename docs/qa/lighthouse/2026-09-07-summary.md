## Accessibility failures found (heading-order)

Digging into the four 98-scoring pages' JSON reports, every one failed the same Lighthouse audit,
`heading-order` ("Heading elements are not in a sequentially-descending order"):

1. **`/governance` and `/governance/documents`-style document lists** — `_DocRow.cshtml`
   (`src/Triathlon.Web/Areas/Public/Shared/_DocRow.cshtml`) hard-coded every row title as `<h4>`
   regardless of where the list sat in the page outline. On `Governance/Index.cshtml` the list
   follows an `<h2>` ("Recently published"), so the row title skipped straight from h2 to h4.
2. **`/events/{slug}` (event detail pages)** — after the fix above, the *same audit* still failed:
   the shared footer (`_Footer.cshtml`) renders its three columns as `<h3>` unconditionally. An
   event detail page has only an `<h1>` in its main content (no `<h2>` — "About the race" uses a
   `<span class="eyebrow">`, not a heading), so the page went straight from h1 to the footer's h3.

## Fixes

1. **`DocRowModel.HeadingLevel`** (`src/Triathlon.Web/Areas/Public/Shared/DocRowModel.cs`) — new
   `int HeadingLevel = 4` parameter; `_DocRow.cshtml` now renders `<h{HeadingLevel}>` (HTML-encoded
   title) instead of a fixed `<h4>`. Each page passes the level that keeps its own outline
   sequential:
   - `Governance/Index.cshtml` ("Recently published" doc list, after an `<h2>`) → `HeadingLevel = 3`
   - `Governance/Documents.cshtml` (doc list right after the page `<h1>`, no `<h2>`) → `HeadingLevel = 2`
   - `Rules.cshtml` ("Regulations library" doc list, after an `<h2>`) → `HeadingLevel = 3`
   - `Training/Guide.cshtml` ("Take the plan with you" doc list, after an `<h2>`) → `HeadingLevel = 3`
   - `Training/Index.cshtml` (doc list nested inside a guide card's `<h3>`) → default `4` (unchanged;
     already correct — this is the context the old hard-coded `<h4>` matched)
2. **Footer columns `<h3>` → `<h2>`** (`_Footer.cshtml`, plus the matching `.footer-grid h3` ->
   `.footer-grid h2` CSS selectors in `site.css`, purely a selector rename — same font, size, colour,
   spacing). The footer is site-wide, so it needs a level that stays valid on every page, including
   ones whose main content never goes past `<h1>`; `<h2>` is a decrease-or-equal from every page's
   heading depth, which the `heading-order` rule always allows (only a *skip going deeper* is a
   violation). Updated the existing `PublicShellTests.Footer_columns_are_h3` test to
   `Footer_columns_are_h2` to match, and to assert no `<h3`/`<h4` remains in the footer.

No layout, colour, spacing, or motion changed — both fixes are heading *tag* changes only, styled
by their existing class-scoped CSS rules.

## What was already correct (no change needed)

Reviewed against the brief's typical-fix list and found already in place:

- `font-display: swap` on every `@font-face` in `wwwroot/css/fonts.css`.
- `<link rel="preload">` in `_Layout.cshtml` scoped to only the two faces used above the fold per
  culture (Tajawal 800 display weight + the culture's 400 body weight), not the whole font set.
- The home hero is an inline `<svg>` course diagram plus text, not an `<img>` — no LCP image,
  no `fetchpriority`/dimensions concern there.
- Below-the-fold `<img>` tags (event gallery, news post hero, footer brand mark) already carry
  `loading="lazy"`; the header brand mark (above the fold) is eager by omission, which is correct.
- The event gallery already reserves space with `aspect-ratio: 4/3` in CSS, so no CLS risk once a
  gallery has images (none of the tested pages currently do).
- `MapStaticAssets()` (`Program.cs`) fingerprints and cache-controls static assets; pre-compressed
  `.br`/`.gz` siblings exist for CSS/JS/etc. in the publish output and are non-zero-byte.
- Response compression (`CompressionSetup.cs`) is enabled and applies over plain HTTP regardless of
  the `EnableForHttps` flag (that flag only gates compression over TLS, for BREACH-class reasons
  irrelevant to this anonymous, identical-per-visitor public site).
- CLS was already 0 (or noise-level 0.001-0.002) on every page in the baseline run — no stat-band or
  layout-shift fix was needed.
